# Legal research: contact data, supervisory authorities, Art. 12 and 15 rules

Research date: 2026-09-25 (v2, verified). Read-only fetches of the datenanfragen/data repo (raw files + GitHub API), the datenanfragen/website source, BlnBDI/BfDI sites, EDPB Guidelines 01/2022 v2.0 (PDF, paragraph numbers below), EUR-Lex/CURIA, BAG case notes.

## Contact data sources

**datenanfragen.de open data** – github.com/datenanfragen/data, licence **CC0 1.0** (`LICENSE` file, GitHub `spdx_id: CC0-1.0`; README: contributions released under CC0). Bundle, modify, no attribution.
- Size (git tree, 2026-09-25, not truncated): **3,068** `companies/*.json`, **57** `supervisory-authorities/*.json`, 117 `obsolete-records/` (slug redirects), 3 `company-packs/` (`all.json`, `at.json`, `de.json`), templates in 12 languages (`templates/de/` = 22 files). Last commit 2026-09-09 ("Update 'marbis GmbH' (community contribution)"), last push 2026-09-13; community PRs land weekly. Default branch `master`.
- Schemas: `schema.json` (company), `schema-supervisory-authorities.json`, `schema-company-packs.json`, `schema-obsolete-records.json`; all `additionalProperties: false`, validated in CI (`yarn test`).
- **Company schema, all properties** (required marked *): `slug`*, `relevant-countries`* (ISO-2 codes or `all`), `name`*, `address`* (country in last line), `sources`* (URLs), `quality`* (enum `tested` > `verified` > `imported` > `scraped`), `categories` (enum incl. `ads`, `credit agency`, `commerce`, `social media`, ...), `runs` (sub-brands/services the controller is responsible for, Art. 4(7)), `phone`, `fax` (international format), `email`, `webform` (privacy-specific form URL), `pgp-fingerprint`, `pgp-url`, `web`, `required-elements` (array of `{desc, type ∈ input|textarea|email|address|name|birthdate, optional?}` — only confirmed elements, the minimum the company needs to identify the person), `request-language` (ISO 639-1), `custom-access-template` / `custom-erasure-template` / `custom-rectification-template` / `custom-objection-template` (path to template file), `needs-id-document` (bool; only `true` if an ID document is confirmed necessary for *all* requests), `suggested-transport-medium` (enum `fax|letter|email|webform`; default chain fax → letter → email), `comments` (array of strings), `facet-group` (`church|school`), `nsfw` (true only).
- Variance in practice: `amazon-de` = Amazon Europe Core SARL, 14 `runs` (amazon.de/.at/.ch, Kindle, Marketplace ...), `email eu-privacy@amazon.de`, `required-elements` name + account e-mail, transport email, comment pointing to the self-service DSAR page; **no** `needs-id-document`, no custom template. `zalando` = only address/phone/fax/email, transport email, no `required-elements` at all. `adsquare` (ad-tech) = `privacy@adsquare.com` plus `webform`, categories `ads`, no `required-elements`. `schufa` is the record with `needs-id-document`-style hints in `comments`. So the drafting step must handle: no required elements (ask user for name+address+e-mail as default), `runs` (list them in the letter — the DE template has a `[runs>...]` block), `webform`-only companies (agent cannot send; hand over to user), and custom templates (only 8 German `access-*` templates exist, all for public bodies/churches/one data-leak case — none for commercial companies).
- `company-packs/de.json`: German suggested pack, groups `address-brokers` (13 slugs, `add-all`: acxiom, az-direct, crifbuergel, deutsche-post-adress, schober, regis24 ...), `credit-agencies` (7, `add-all`: schufa, crifbuergel, infoscore, regis24 ...), and `choose` groups `commerce` (20: amazon-de, zalando, otto, ebay-de, lidl ...), `entertainment`, `finance` (16), `insurance` (26), `telecommunication`, etc. This is a ready-made "send to everyone who has data on you" starter set.
- Access: `git clone` (or GitHub tarball) is the documented way; there is no documented public API. The website queries a **Typesense** instance at `https://search.datenanfragen.de` with an empty API key (`src/Utility/search.ts`: `query_by: name, runs, web, slug, address, comments`, filter `relevant-countries:[de, all]`). It is undocumented, unversioned and did not answer from this network — treat as unofficial; ship the repo snapshot and refresh it via git.

**Fallback lookup** when a company is missing: fetch `/datenschutz`, `/datenschutzerklaerung`, `/privacy`, then the Impressum; extract mailto/addresses near "Datenschutzbeauftragte", "datenschutz@", "privacy@", "dpo@". Art. 13(1)(a)-(b) requires contact details of the controller and, where present, of the DPO (Art. 37(7)), so German privacy pages almost always carry one. Show the extracted address for confirmation; offer to open a PR upstream (company-json.datenanfragen.de generates valid records).

## Supervisory authorities

- Authority schema properties (required *): `slug`*, `relevant-countries`*, `name`*, `address`*, `sources`*, `phone`, `fax`, `email`, `webform`, `pgp-fingerprint`, `pgp-url`, `web`, `complaint-language`, `suggested-transport-medium` (`fax|letter|email` only), `comments`. **No jurisdiction field** (no Land, no postcode range, no mapping to companies): the Land must be derived from the company `address` (postcode → Land table) with the user's own Land as fallback.
- 26 German files: 17 Land authorities (Bavaria has two: `debaylda` = BayLDA for companies, `debayldb` = BayLfD for public bodies), `debfdi`, and 8 church authorities (`deekdbfd`, `dekath*`, `derf`, `derfdw`).
- Berlin `deberlbdi.json` (verified): Alt-Moabit 59-61, 10555 Berlin; `mailbox@datenschutz-berlin.de`; `webform https://kontakt.datenschutz-berlin.de/`; PGP key published; `complaint-language de`; transport email. BfDI `debfdi.json`: Graurheindorfer Str. 153, 53117 Bonn; `poststelle@bfdi.bund.de`; webform `https://formulare.bfdi.bund.de/lip/action/invoke.do?id=BfDIBeschwerde`; PGP; de; email.
- Competence rules to encode: non-public bodies → authority of the Land of the establishment (§ 40 BDSG; several establishments → Art. 4(16) main-establishment logic). BfDI is competent only for federal public bodies and **telecommunications/postal companies** (§ 9 BDSG) — e.g. a Telekom complaint goes to BfDI, not Bonn's Land authority. Art. 77(1) lets the person file in the Land of residence/work/infringement; the receiving authority forwards ("Beschwerden über Stellen aus anderen Bundesländern und Bundesbehörden geben wir an die jeweils zuständige Aufsichtsbehörde ab", BlnBDI). Filing with the correct authority saves weeks.
- **BlnBDI online form** (`https://kontakt.datenschutz-berlin.de/`, verified 2026-09-25): required fields = surname, first name/pseudonym, postal address **or** public PGP key (for the reply), description of facts, description of the alleged violation, controller name + address; optional = phone, e-mail, "bisherige Maßnahmen"; role selector (Kunde, Angestellter, Werbeempfänger, ...); uploads PDF/images/PGP key. The form states that meaningful evidence (request, confirmations, screenshots) is needed, otherwise processing is delayed or a procedure may not be opened. Prior contact with the company is **recommended, not required** ("Wir empfehlen Ihnen, sich zunächst direkt an die Daten verarbeitende Stelle zu wenden"); the authority normally forwards the complaint to the controller for a statement. Vague, unspecific submissions do not trigger a formal Art. 77 procedure. Consequence for the agent: the complaint draft must contain the controller's exact name/address, the request date, the reminder date, the deadline computation and attach the ledger (sent letter, delivery evidence, any reply).
- Templates `templates/de/`: `access-default.txt` (asks confirmation, copy of *all* data incl. pseudonymised data, items 1-6 of Art. 15(1), Art. 46 safeguards, optional Art. 20 block, `[runs>]` block, one-month deadline, free of charge, `[has_fields>{id_data}]`), `access-tracking.txt` (ad-tech: user should add device/cookie IDs), `admonition.txt` (sets a 2-week grace period and announces complaint), `complaint.txt` (Art. 77 letter with `{request_date}`, `{request_article}`, `{request_recipient_address}`, optional anonymity request), plus erasure/objection/rectification and church/police variants. Syntax: `{var}`, `[flag>...]`, `<italic>`.

## Legal rules & reply state machine

Rules to encode in code (not the LLM); sources in brackets:
- **Deadline**: without undue delay, at most one month from **receipt** through an official channel; awareness not required (EDPB 01/2022 §157, §159). Extension by up to two further months only if the person is told the reasons within the first month; an extension is the exception and "should not be overused"; large volume alone does not justify it (§162-164). Separate duty: if the controller will not act, it must say so with reasons and remedies within one month (Art. 12(4), §157).
- **Month computation**: EDPB §160 applies **Regulation (EEC, Euratom) 1182/71**: request received 5 March → due 5 April inclusive (Ex. 32); received 31 August → due 30 September, the last day of the following month when there is no corresponding date (Ex. 33); last day on a weekend or public holiday → next working day (§161). National law may define when a message counts as received (fn. 90); German §§ 187-188, 193 BGB give the same result. Public-holiday table must be per Land of the controller.
- **Identity check / clock**: the clock does **not restart**, but EDPB §159 + Ex. 31 allow a **suspension** while the controller waits for identity information it requested *without undue delay* on reasonable doubt (Art. 12(6)); the same for a Recital 63 request to specify the processing. A late or unfounded ID request does not suspend. What may be asked: only what is necessary (§65, §68); already-authenticated users (account login, known e-mail) must not be asked for an ID copy (§73); an ID copy is "generally not an appropriate way of authentication" and only justified for high-risk data such as health (§74-75, §78); fields like number, photo, MRZ, nationality may be redacted; expiry date, issuing authority and matching full name suffice (§76). BfDI: usually name, address, date of birth and validity suffice; everything else blackened. Agent rule: never send an ID automatically; present the demand with this guidance, log the request date, mark the clock suspended from ID-request date until the user replies, then resume.
- **Free of charge**: first copy free regardless of purpose (Art. 15(3); CJEU C-307/22, 26 Oct 2023). A new request about a different time/scope is again a free first copy, even shortly after (EDPB §28, Ex. 2).
- **Content owed** (Art. 15(1) a-h + 15(3)): purposes, categories, **named** recipients unless identification is impossible or the request is manifestly unfounded/excessive (C-154/21, 12 Jan 2023), retention or criteria, rights, complaint right, source, automated decisions incl. "the procedure and principles actually applied", concise and intelligible, trade secrets to be weighed by the authority/court rather than refused outright (C-203/22, 27 Feb 2025), third-country safeguards, and a copy that is a faithful and intelligible reproduction, including document/database extracts where needed for intelligibility (C-487/21, 4 May 2023; C-307/22). A controller must also answer "no data" explicitly (Art. 15(1) first limb) and may not delete first and then deny (§ Ex. 6).
- **Electronic form**: if the request was made electronically, all Art. 15(1)-(2) information and the copy must be provided in a commonly used electronic form unless the person asks otherwise (Art. 12(3), 15(3) s. 3; EDPB §32, §134; BfDI). A paper-only reply to an e-mail request is a format defect worth a follow-up, not a reason to treat the request as unanswered.
- **Manifestly unfounded / excessive** (Art. 12(5)): to be read narrowly; the controller bears the burden and must explain to the person and, on request, to the authority (§175-176). "Excessive" is mainly about repetition at unreasonable intervals, judged per sector: a social-media user every three months is not excessive (Ex. 40), a credit-agency request at short intervals is fine (Ex. 41), a carpenter every two months is (Ex. 39). Instead of refusing, the controller may charge a reasonable fee. Rule: one request per company per 12 months is always safe; 3-6 months for platforms, ad-tech and credit agencies; sending to many *different* companies at once is never excessive.
- **Damages**: mere delay is not a non-material damage under Art. 82; the person must show concrete consequences (BAG 20 Feb 2025, 8 AZR 61/24). Practical levers: reminder, Art. 77 complaint, Art. 79 court action. The agent must not promise damages.

## Corrections to the previous version
1. Company count is 3,068 files (was "~3,000"), 117 obsolete records; last commit 2026-09-09.
2. `quality` is a **required** field; `comments` is an array; company `suggested-transport-medium` also allows `webform`; the schema also has `custom-erasure/rectification/objection-template`, `facet-group`, `nsfw`, `pgp-*`, `webform`; `required-elements.type` is an enum with `optional` flag. Amazon has no `needs-id-document`; Zalando has no `required-elements`.
3. Authority records have a `comments` field and **no jurisdiction field**; Bavaria has two authorities; BfDI competence limited to federal bodies and telecom/post companies (§ 9 BDSG).
4. BlnBDI: prior contact is explicitly *recommended* (not merely "no prerequisite"); the form has hard required fields and demands evidence; vague complaints do not open a procedure.
5. Month rule corrected: EDPB applies Reg. 1182/71 with the end-of-month rule (31 Aug → 30 Sep), not simply "same day next month".
6. Identity check: the clock is *suspended* (not "paused only if doubt justified" in the abstract) when the controller asked promptly on reasonable doubt, and resumes after the reply; Recital 63 clarification requests suspend likewise; already-authenticated users cannot be asked for an ID copy.
7. Excessive requests: "once per company per year" replaced by the EDPB sector-dependent interval test (quarterly is fine for platforms/credit agencies); fee instead of refusal; burden on controller.
8. Added: electronic-form duty, explicit "no data" answer, Art. 12(4) refusal notice, C-203/22 holding ("procedure and principles actually applied", trade-secret balancing by authority), judgment dates, states `clarification-requested`, `no-data`, `refused` (split), `complaint-filed`.
9. The Typesense search endpoint is unofficial and unverified; git clone stays the integration path.
